[#_versioning]
== Versioning

{rte-short-name} uses https://semver.org/[semantic versioning]. A version
follows the `MAJOR.MINOR.PATCH` pattern. The supported version is the
latest release.

Two deliverables follow this version:

* The `runtime-enforcer` Helm chart, in its `appVersion` field. The
  controller, the agent, and the debugger images carry this version as
  their tag.
* The `kubectl runtime-enforcer` plugin binary.

[#_version_compatibility_among_components]
== Version compatibility among components

The Helm chart `appVersion` and the `kubectl runtime-enforcer` plugin must
run the same `MAJOR.MINOR.PATCH` version. If the chart runs `appVersion`
`0.10.1`, install the plugin binary from the `v0.10.1` release.

[#_helm_chart_versions]
== Helm chart versions

A Helm chart has two version fields. The `appVersion` field holds the
{rte-short-name} version described above. The `version` field is the
version of the chart itself. It also follows semantic versioning, and it
describes changes to the chart templates and to `values.yaml`.

The two fields do not move together. When you
plan an upgrade, read the `appVersion` of the target chart.

[#_upgrade_paths]
== Upgrade paths

You can upgrade across several `PATCH` versions in one operation. You
cannot upgrade across more than one `MINOR` or `MAJOR` version in one
operation.

For example, you can upgrade from `0.10.0` to `0.10.1` in one step. You
cannot upgrade from `0.9.0` to `0.11.0` in one step. Upgrade from `0.9.0`
to `0.10.x` first, then from `0.10.x` to `0.11.0`. To move across a
`MAJOR` version, apply every `MINOR` version between the two.

[#_upgrade_order]
== Upgrade order

Upgrade the `runtime-enforcer` Helm chart first. The chart upgrades the
controller, the agent, and the debugger together. Then install the
`kubectl runtime-enforcer` plugin binary from the same release.

The agent DaemonSet uses a rolling update with a surge. The new agent pod
on a node loads every policy and binds every running pod before the old
pod stops. Protection does not lapse during the upgrade. See
xref:explanations/architecture.adoc[Architecture] for the sequence.

[#_downgrades]
== Downgrades

{rte-short-name} does not support downgrades, and the project does not
test them.

[#_policies]
== Policies

A `WorkloadPolicy` carries no version of its own. It holds a mode and an
allow-list, and it stays in the cluster across {rte-short-name}
upgrades. You do not rewrite or re-apply your policies when you upgrade.
