{admc-name} v1.17.0 removed the cert-manager dependency. Since then, the
{admc-short-name} controller manages the certificates of the stack. It
rotates each certificate before it expires, and it keeps the CA bundle of
each webhook configuration correct.

The Helm chart creates the first certificates, because the controller needs
its own certificate before it can start. After the installation, the
controller does the rotation. All the certificates use ECDSA P-256 keys.

[#_certificates_and_secrets]
== The certificates and their secrets

The stack uses one root CA. The root CA signs all the other certificates.
Each certificate is in a secret in the namespace of the {admc-short-name}
stack, for example `kubewarden`.

[cols="2,2,1,1,3"]
|===
|Certificate |Secret |Created by |Valid for |Used by

|Root CA
|`kubewarden-ca`
|Helm chart
|10 years
|The API server and the audit scanner use it to check the server certificates.
With mTLS, the policy servers use it to check the client certificate of the audit scanner.

|Server certificate of the controller
|`kubewarden-webhook-server-cert`
|Helm chart
|1 year
|The webhook server of the controller. The API server calls this server to
check and change the {admc-short-name} resources, for example
`ClusterAdmissionPolicy` and `PolicyServer`.

|Server certificate of a policy server
|`policy-server-<name>`
|Controller, when you create the `PolicyServer`
|1 year
|The policy server. The API server and the audit scanner call this server to
evaluate the policies.

|Client certificate of the audit scanner
|`kubewarden-audit-scanner-client-cert`
|Helm chart
|1 year
|The audit scanner. The policy servers check it only when mTLS is enabled.
|===

The controller rotates all these certificates. The `kubewarden-ca` secret
holds the current root CA in `ca.crt` and `ca.key`. After a rotation of the
root CA, it also holds the previous root CA in `old-ca.crt`.

[#_ca_bundles]
== The CA bundles of the webhook configurations

The API server calls a webhook server only if it trusts the server
certificate. It checks the certificate with the CA bundle (`caBundle`) of the
webhook configuration. The CA bundle contains `ca.crt` of `kubewarden-ca`. If
the secret holds `old-ca.crt`, the CA bundle contains it too.

The controller writes the CA bundle of two groups of webhook configurations:

* The webhook configurations of the controller,
`kubewarden-controller-validating-webhook-configuration` and
`kubewarden-controller-mutating-webhook-configuration`. The Helm chart
creates them with the annotation
`kubewarden.io/inject-ca-from: <namespace>/kubewarden-ca`. The controller
watches these webhook configurations and the `kubewarden-ca` secret. If a CA
bundle is not correct, the controller writes the correct one within seconds.
A GitOps tool or a manual change can cause a CA bundle that is not correct.
* The webhook configuration of each policy. The controller creates it and
writes its CA bundle. When the `kubewarden-ca` secret changes, the controller
writes the new CA bundle into each of them. It does this also while a
`PolicyServer` rolls out new pods.

The controller ignores the `kubewarden.io/inject-ca-from` annotation when it
names a secret other than its own `kubewarden-ca` secret.

[#_rotation]
== When the controller rotates a certificate

The controller checks all the certificates when it starts, and then every 12
hours. If the check at startup fails, the controller makes up to 8 tries in
about 4 minutes. For example, the check fails when the API server is not
available.
Only one controller instance does the check: the instance that holds the
leader `Lease` in the namespace of the stack.

The controller rotates a certificate if one of these conditions is true:

* The certificate expires in less than 60 days.
* The certificate is already expired.
* The current root CA did not sign the certificate.

Thus a certificate that expired while the cluster was stopped gets a
replacement at the next start of the controller.

The controller signs a new server certificate only when the webhook
configurations that call this server trust the root CA. Before it signs the
certificate, it waits until their CA bundles contain the current root CA. If
this does not occur within 2 minutes, the controller keeps the current
certificate. It tries again at the next check.

The client certificate of the audit scanner does not wait, because no
webhook configuration checks it.

[#_root_ca_rotation]
== Rotation of the root CA

The controller rotates the root CA 60 days before it expires. The rotation
occurs in these steps:

. The controller creates a new root CA. It writes the new root CA to `ca.crt`
and `ca.key`. It moves the previous root CA to `old-ca.crt`.
. Within seconds, the controller writes the new CA bundle into each webhook
configuration. The new CA bundle contains both root CAs.
. The controller waits until the CA bundles contain the new root CA. Then it
signs new server certificates and a new client certificate with the new root
CA.
. The components load the new certificates. While some components still use
the previous certificates, the API server accepts both. The reason is that
each CA bundle contains both root CAs.
. At the first check after the previous root CA expires, about 60 days
later, the controller removes `old-ca.crt`. Then it writes the CA bundle with
the new root CA only.

The order of the steps prevents downtime. No server uses a certificate before
its webhook configuration trusts the root CA that signed it.

With mTLS, the policy servers check client certificates with `ca.crt` of
`kubewarden-ca`, not with `old-ca.crt`. When a policy server loads the new
root CA, it rejects a client certificate that the previous root CA signed.
The next run of the audit scanner uses its new client certificate. If a run
of the audit scanner is in progress during the rotation, some of its requests
can fail. The next run corrects the policy reports. Admission requests are
not affected.

[#_loading_new_certificates]
== How the components load a new certificate

No component restarts to load a new certificate.

[cols="1,3"]
|===
|Component |How it loads a new certificate

|Controller
|The webhook server watches the files of its mounted secret. It loads a new
certificate after the kubelet updates these files, usually within about one
minute.

|Policy server
|The policy server watches the directories of its mounted secrets. It loads a
new server certificate, a new root CA, or a new client CA. It does this after
the kubelet updates the files, usually within about one minute.

|Audit scanner
|Each run of the `audit-scanner` CronJob starts a new pod. The pod reads the
current certificates.

|API server
|The API server uses the current CA bundle of each webhook configuration. A
new CA bundle has an effect on the next request.
|===

[#_recovery]
== Recovery from expired certificates

If certificates expired, the API server cannot call the webhook servers. Then
each webhook with `failurePolicy: Fail` rejects the requests that it matches.
This can occur after the cluster was stopped for a long time.

The commands in this section use the namespace `kubewarden` and the release
name `admission-controller`. If your installation uses other names, change
the commands. If the controller has more than one replica, read the logs of
the pod that holds the leader `Lease`.

[#_recovery_restart_the_controller]
=== Restart the controller

The controller rotates the expired certificates when it starts. Use this
procedure when the `kubewarden-ca` secret exists.

. Restart the controller:
+
[source,console]
----
kubectl -n kubewarden rollout restart deployment admission-controller
----
. Make sure that the controller rotated the certificates:
+
[source,console]
----
kubectl -n kubewarden logs deployment/admission-controller | grep "rotated successfully"
----
. Wait about one minute. The components then load the new certificates.

[#_recovery_create_a_new_root_ca]
=== Create a new root CA

The controller does not create the root CA. Only the Helm chart creates it.
Use this procedure when the `kubewarden-ca` secret is missing or damaged.

[CAUTION]
====
Delete the three secrets of the Helm chart together. If you keep the old
certificates, the webhooks of the controller fail until the controller signs
new certificates.
====

. Get the version of the installed chart. The `CHART` column shows it:
+
[source,console]
----
helm list -n kubewarden
----
. Delete the three secrets of the Helm chart:
+
[source,console]
----
kubectl -n kubewarden delete secret kubewarden-ca kubewarden-webhook-server-cert kubewarden-audit-scanner-client-cert
----
. Upgrade the release with the same chart version and the same values. Replace `<VERSION>` with the version of step 1:
+
[source,console]
----
helm upgrade --wait -n kubewarden admission-controller kubewarden/admission-controller --version <VERSION> --reuse-values
----
. Make sure that the controller rotated the certificates of the policy servers:
+
[source,console]
----
kubectl -n kubewarden logs deployment/admission-controller | grep "rotated successfully"
----

The Helm chart creates a new root CA and new certificates for the controller
and the audit scanner. The upgrade restarts the controller. At startup, the
controller signs new certificates for the policy servers, because the new
root CA did not sign the previous ones.

The previous root CA is not available, so the CA bundles contain only the new
root CA. Until the policy servers load their new certificates, usually within
about one minute, the policies with `failurePolicy: Fail` reject requests.

[#_limits]
== Policies in the namespace of the stack

A policy with `failurePolicy: Fail` that covers the namespace of the
{admc-short-name} stack can stop the rotation.

By default, a `ClusterAdmissionPolicy` or a `ClusterAdmissionPolicyGroup`
does not cover this namespace. The setting
`allowInsideAdmissionControllerNamespace: true` removes this protection. An
`AdmissionPolicy` or an `AdmissionPolicyGroup` in this namespace always
covers it.

If the certificate of its policy server expired, such a policy rejects each
request that it matches. The policy does not run, because the API server
cannot call the policy server. For this reason, the
`KUBEWARDEN_ALWAYS_ACCEPT_ADMISSION_REVIEWS_ON_NAMESPACE` environment
variable has no effect in this case.

* If the policy matches `Secret` resources, the controller cannot write the
new certificates.
* If the policy matches `Lease` resources, the controller cannot keep its
leader `Lease`. Then it does not check the certificates.

For more information, refer to
xref:howtos/policies-eval-resources-in-controller-namespace.adoc[].
