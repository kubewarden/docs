[#_prerequisites]
== Prerequisites

Before you start, you need:

* A Kubernetes cluster you can throw away, for example a link:https://kind.sigs.k8s.io/[kind] cluster.
  This guide creates one for you.
* `kubectl`, `helm` and `curl` installed locally.
* {cert-manager-term} and `cert-manager-csi-driver` in the cluster.
  They issue the TLS certificates of the bundled {opentelemetry-collector-term}.
  With the Istio provider, in the default TLS mode `issuer`, they also issue
  the certificate of the controller endpoint that receives the ztunnel logs.

[NOTE]
====
This page documents the chart in this repository (`charts/network-enforcer`), for
{ne-short-name} version `0.2.0` and later.
Every `--set` flag used here exists in `charts/network-enforcer/values.yaml`.
====

[#_choose-your-provider]
== Choose your provider

{ne-short-name} does not observe traffic on its own: it consumes {flow-term} information from the data plane
already running in your cluster, and it enforces policies with the {native-policy-object-term} API of that data plane.
Pick one provider and follow only its section.

[cols="1,1,2,2,1"]
|===
| Provider | `controller.provider.name` | Learning source | Enforced with | Generated policy backend

| Istio ambient
| `istio` (default)
| {ztunnel-term} access logs, tailed by the `istio-fluent-bit` DaemonSet and pushed to the controller over OTLP
| Istio {authorizationpolicy-term}
| `backend: istio`

| Calico
| `calico`
| Calico {goldmane-term} flow API over mTLS (`goldmane.calico-system.svc:7443`)
| Kubernetes {networkpolicy-term}
| `backend: kubernetes`

| Cilium
| `cilium`
| {hubble-relay-term} gRPC API over mutual TLS (`hubble-relay.kube-system.svc:443`)
| Kubernetes `NetworkPolicy`
| `backend: kubernetes`
|===

Each provider has its own endpoint value: `controller.provider.istio.endpoint`,
`controller.provider.calico.endpoint`, and `controller.provider.cilium.endpoint`.
The defaults are the values listed above. For `istio`, the value is the local
OTLP port, `4317`.

[#_option-1-istio-ambient]
=== Option 1: Istio ambient

The Istio ambient path keeps the cluster CNI in place and layers the ambient data plane on top of it,
so a plain kind cluster with its default CNI is enough:

[source,bash]
----
kind create cluster --name network-enforcer
----

Download `istioctl` and install the ambient profile:

[source,bash]
----
curl -L https://istio.io/downloadIstio | ISTIO_VERSION=1.30.3 sh -

./istio-1.30.3/bin/istioctl install --set profile=ambient \
  --set values.cni.ambient.ipv6=false \
  --set values.pilot.env.AMBIENT_ENABLE_DRY_RUN_AUTHORIZATION_POLICY=true \
  --set values.ztunnel.env.AUTHZ_POLICY_INFO_LOGGING=true \
  --set values.ztunnel.logAsJson=true \
  --skip-confirmation
----

These `--set` flags are not optional for {ne-short-name}:

* `AMBIENT_ENABLE_DRY_RUN_AUTHORIZATION_POLICY` lets `ztunnel` evaluate the {dry-run-term} `AuthorizationPolicy`
  that `monitor` mode installs, without blocking traffic.
* `AUTHZ_POLICY_INFO_LOGGING` makes `ztunnel` log the policy decision of every connection.
* `logAsJson` makes `ztunnel` emit JSON access logs, which is the format the `istio-fluent-bit` pipeline
  shipped with the chart parses.

The `values.cni.ambient.ipv6=false` flag is not required by {ne-short-name}, but `istio-cni` programs
IPv6 redirection rules by default and fails on IPv4-only nodes, which is what a default kind cluster
gives you.
Drop the flag if your cluster is dual-stack.

Finally, enroll the namespaces you want to observe in the mesh.
Do this *before* creating the workloads: `istio-cni` decides at pod creation time whether a pod's traffic
is redirected to the node `ztunnel`.

[source,bash]
----
kubectl label namespace default istio.io/dataplane-mode=ambient
----

[IMPORTANT]
====
Istio ambient authorization is L4 and identity based, which has three consequences for this guide:

* Only TCP traffic is observed and enforced; UDP does not go through `ztunnel`.
* Rules are written in terms of SPIFFE {principal-term}s, so every workload should have its own
  `ServiceAccount` — otherwise all workloads sharing the default service account share one identity.
* Authorization is enforced on the receiving side, so {ne-short-name} only learns *ingress* proposals.
====

[#_option-2-calico]
=== Option 2: Calico

Calico is the cluster CNI, so create a kind cluster with the default CNI disabled:

[source,bash]
----
curl -sSL https://raw.githubusercontent.com/kubewarden/network-enforcer/main/docs/yaml/kind_cluster.yaml \
  | kind create cluster --name network-enforcer --config=-
----

Then install Calico. If you cloned this repository, run the helper script:

[source,bash]
----
./hack/setup-calico.sh
----

Otherwise, run it straight from the repository:

[source,bash]
----
curl -sSL https://raw.githubusercontent.com/kubewarden/network-enforcer/main/hack/setup-calico.sh | bash
----

The script installs the Calico CRDs and the Tigera operator with
`goldmane.enabled=true`. Then it waits for the ConfigMap `goldmane-ca-bundle`
and the Secret `goldmane-key-pair` that Calico creates in `calico-system`, and
for the Goldmane deployment.

{ne-short-name} reads that key pair and CA bundle from `calico-system` through
the Kubernetes API. The chart creates a Role in `calico-system` for this. You
do not copy a Secret, and you do not create the {ne-short-name} namespace
before the install. Goldmane always requires mutual TLS. There is no
plain-text option.

[IMPORTANT]
====
Run the script *before* installing the {ne-short-name} chart, so that the
Goldmane key pair exists when the controller starts. You can install the
chart in any namespace.

The default TLS mode is `existingSecret`.
The controller reads `tls.crt` and `tls.key` from `goldmane-key-pair`.
It reads the CA from `goldmane-ca-bundle`, key `tigera-ca-bundle.crt`.

If you already have a client Secret in the release namespace, leave
`controller.provider.calico.tls.existingSecret.namespace` empty.
Set `controller.provider.calico.tls.existingSecret.name` to that Secret name,
for example `net-enf-goldmane-client-certs`.
The chart then mounts the Secret.
The Secret must contain `tls.crt`, `tls.key`, and `ca.crt`.
====

[#_option-3-cilium]
=== Option 3: Cilium

Cilium is the cluster CNI, so create a kind cluster with the default CNI disabled:

[source,bash]
----
curl -sSL https://raw.githubusercontent.com/kubewarden/network-enforcer/main/docs/yaml/kind_cluster.yaml \
  | kind create cluster --name network-enforcer --config=-
----

Then install Cilium. If you cloned this repository, run the helper script:

[source,bash]
----
./hack/setup-cilium.sh
----

Otherwise, run it straight from the repository:

[source,bash]
----
curl -sSL https://raw.githubusercontent.com/kubewarden/network-enforcer/main/hack/setup-cilium.sh | bash
----

The script installs Cilium with the values {ne-short-name} needs, and waits for the agent,
the operator and Hubble Relay to be ready:

* `hubble.enabled=true` and `hubble.relay.enabled=true`, because the controller reads flows from the
  Hubble Relay gRPC API.
* `hubble.relay.tls.server.enabled=true` and `hubble.relay.tls.server.mtls=true`,
  because the controller talks to `hubble-relay.kube-system.svc:443` over
  mutual TLS. Cilium creates the client certificate in the Secret
  `hubble-relay-client-certs` in `kube-system`, and {ne-short-name} reads it
  through the Kubernetes API.
* `policyDenyResponse=icmp`, so denied egress traffic is answered with an ICMP error instead of being
  silently dropped.

Use `CILIUM_VERSION` to pick a different Cilium version, for example
`CILIUM_VERSION=1.19.7 ./hack/setup-cilium.sh`.

Use `HUBBLE_RELAY_TLS` to select how the Hubble certificates are made. The
default, `helm`, lets Cilium generate them. The value `certmanager` lets
cert-manager issue them. The value `off` turns Relay TLS off. In that case,
install the chart with `controller.provider.cilium.tls.mode=insecure` and an
empty `controller.provider.cilium.tls.serverName`. The chart then talks to
Relay on port `80` in plain text.

[#_install-cert-manager-and-cert-manager-csi-driver]
== Install cert-manager and cert-manager-csi-driver

Two parts of {ne-short-name} receive TLS certificates from
`cert-manager-csi-driver`. One is the bundled OpenTelemetry collector. The
other is the controller endpoint that receives the ztunnel logs, with the
Istio provider in the default TLS mode `issuer`. Install both components
before the chart:

[source,bash]
----
helm repo add jetstack https://charts.jetstack.io
helm repo update

helm install cert-manager jetstack/cert-manager \
  --namespace cert-manager \
  --create-namespace \
  --set crds.enabled=true \
  --wait

helm install cert-manager-csi-driver jetstack/cert-manager-csi-driver \
  --namespace cert-manager \
  --wait
----

[NOTE]
====
For more information on configuring cert-manager, see the
link:https://cert-manager.io/docs/installation/helm[cert-manager documentation].

If you do not want to install cert-manager, set
`telemetry.collectorStrategy=none` to turn the export off. With the Istio
provider, also set `controller.provider.istio.tls.mode=insecure`, so that the
log endpoint of the controller does not need a certificate. The Calico and
Cilium defaults read an existing Secret, so they do not need cert-manager.
{ne-short-name} then keeps working. Learning, monitor, and protect are not
affected. Violations stay in the policy status but are not exported as
OpenTelemetry logs.
====

[#_install-the-network-enforcer-chart]
== Install the {ne-short-name} chart

[source,bash]
----
helm repo add kubewarden https://charts.kubewarden.io
helm repo update
----

Install the chart with the provider you prepared above (`istio`, `calico` or `cilium`):

[source,bash]
----
helm install network-enforcer kubewarden/network-enforcer \
  --namespace network-enforcer \
  --create-namespace \
  --set controller.provider.name=istio \
  --set controller.wnpStatusUpdateInterval=3s \
  --wait
----

`controller.wnpStatusUpdateInterval` is the interval at which the {controller-term} refreshes the violations in
the status of every `WorkloadNetworkPolicy`.
It is lowered from its default (`30s`) to make this demo responsive; in production you rarely need to
change it.

[NOTE]
====
If you cloned the repository you can install the very same chart from your checkout with
`helm install network-enforcer ./charts/network-enforcer ...`.
====
